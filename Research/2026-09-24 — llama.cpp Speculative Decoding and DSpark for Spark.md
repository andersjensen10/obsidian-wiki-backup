## Decision

The selected topic is **whether llama.cpp’s current speculative-decoding implementations—particularly DSpark—justify a local Spark experiment, and how to benchmark them without confusing upstream GPU results with AJ’s actual service behavior**.

## Executive finding

llama.cpp now documents several speculative-decoding paths, including ordinary draft models, EAGLE-3, DFlash, DSpark, MTP, and multiple n-gram methods.[1] DSpark combines DFlash-style block drafting with a semi-autoregressive Markov head, and the upstream pull request reports substantial speedups on Qwen3 benchmarks.[2]

The opportunity is real but conditional.[unverified] Speculative decoding helps when draft tokens are accepted often enough and the verification batch is cheaper than serial target decoding; the upstream documentation describes this mechanism directly.[1] The published DSpark numbers were measured on an RTX 4090 with Qwen3 targets, greedy decoding, and specific prompt categories, not on AJ’s Spark topology.[2]

**Recommendation:** run a disposable A/B benchmark against the exact Spark target model and serving configuration before changing the service. Start with the least invasive candidate, `ngram-mod`, if the goal is to test shared-server behavior without downloading a second model; then test a target-matched DSpark draft only if the first measurement shows that speculative verification is beneficial for AJ’s workload.[unverified]

## Sourced facts

### 1. llama.cpp has moved beyond one speculative-decoding implementation

The current llama.cpp documentation lists `draft-simple`, `draft-eagle3`, `draft-dflash`, `draft-dspark`, `draft-mtp`, `ngram-cache`, `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`, and `ngram-mod` as speculative-decoding types.[1]

The documented approaches have different dependencies. EAGLE-3 uses target hidden states and a target-specific one-layer draft; DFlash emits a block of draft tokens in one forward pass; DSpark adds a previous-token-conditioned Markov bias to the DFlash-style block; n-gram methods reuse patterns from token history rather than loading a second neural draft model.[1]

This matters operationally: “try speculative decoding” is not one experiment. A draft-model path changes model loading, VRAM use, conversion, and compatibility, while an n-gram path changes server state and may be much cheaper to stage.[unverified]

### 2. DSpark is target-specific and currently documented around Qwen3

The llama.cpp documentation describes DSpark as a DeepSpec checkpoint trained for a specific target and gives `deepseek-ai/dspark_qwen3_4b_block7` paired with `Qwen/Qwen3-4B` as an example.[1] The DSpark pull request says the initial implementation supports Qwen3-backed drafts and that the draft reuses the target tokenizer and token embeddings during conversion.[2]

The documented launch path requires a target model, a DSpark draft model, `--spec-type draft-dspark`, a draft length such as `--spec-draft-n-max 7`, and `--jinja` in the example.[1][2] The pull request specifically says that this path should use `llama-server` or `llama-cli`, because it needs target hidden states and KV-cache injection.[2]

The practical consequence for AJ is that DSpark is not a drop-in client-side flag for the current remote API. It requires a compatible llama.cpp server build, a target-matched draft artifact, and a model-loading plan that fits Spark’s memory budget.[unverified]

### 3. Upstream DSpark results are promising but not portable guarantees

The DSpark pull request reports Qwen3-8B results on an RTX 4090, with greedy decoding and `--spec-draft-n-max 7`; its qualitative split reports 1.88× overall decode speedup versus the no-draft baseline and 1.21× versus DFlash.[2]

The same pull request reports substantially higher gains on selected Qwen3-4B and quantized Qwen3-8B benchmark suites, but the results vary by domain: the reported Qwen3-8B Q4_K_M DSpark geomean is 1.81×, while the reported MT-Bench speedup is only 1.12×.[2]

Those figures support testing, not adoption. They come from the contributor’s benchmark setup, model variants, prompt sets, and greedy settings; they do not establish expected speed on Spark, on AJ’s aggressive Qwen3 configuration, with thinking disabled, or under real queueing and concurrency.[unverified]

### 4. Verification preserves greedy output, but sampling behavior needs its own test

The DSpark pull request states that greedy decoding is lossless because the draft only proposes tokens and the target model verifies them; it says the output matches non-speculative greedy decoding.[2]

The llama.cpp documentation also warns that stochastic CPU and backend sampling can select different tokens because floating-point operations and device paths may differ, and it recommends greedy sampling for exact output matching.[1]

Therefore the first AJ benchmark should separate two questions:

- **Performance equivalence:** with deterministic greedy decoding, does speculative mode preserve the baseline output while reducing decode time?
- **Production behavior:** with AJ’s actual sampling and chat-template settings, does it preserve acceptable output quality and tool/format behavior?

A green result on the first question does not prove the second.[unverified]

### 5. n-gram methods offer a low-cost control condition

The documentation describes `ngram-mod` as a lightweight hasher with approximately 16 MB of memory, constant memory and complexity, variable draft lengths, and a hash pool shared across server slots.[1]

It gives example parameters including `--spec-ngram-mod-n-match 24`, `--spec-ngram-mod-n-min 48`, and `--spec-ngram-mod-n-max 64`, while warning that small n values are not recommended and that MoE models may require long drafts.[1]

This makes `ngram-mod` useful as a control condition, not necessarily as the best final optimization.[unverified] It can reveal whether AJ’s workload contains enough repetition for cheap self-speculation before the more invasive DSpark path is attempted.[unverified]

### 6. llama-server exposes the observability needed for a bounded test

The llama-server documentation lists speculative decoding, monitoring endpoints, parallel decoding, continuous batching, schema-constrained JSON, and function calling among the server’s features.[3]

The speculative-decoding documentation says each implementation prints statistics such as draft acceptance rate, generated and accepted draft tokens, and timing fields for some n-gram implementations.[1] It also points to the SPEED-Bench client, which compares a baseline server against a speculative-decoding server across throughput, latency, and acceptance.[1]

The server documentation also exposes JSONL logging and performance-related server controls, which should make it possible to collect machine-readable run records rather than relying on visually reading logs.[3] The exact fields emitted by AJ’s active build must be checked locally.[unverified]

## Analysis for AJ’s Spark setup

### Why this is relevant now

AJ’s Spark service is already a single-slot local inference service, so reducing serial decode time could improve both response latency and the queue experienced by delegated work.[unverified] Speculative decoding is especially relevant to this topology because a faster completed turn may be more valuable than a higher theoretical multi-user throughput number.[unverified]

The main risk is that a draft model adds memory pressure and may make model startup or VRAM fitting worse.[unverified] A draft that performs well on an RTX 4090 may be a poor trade on Spark if it forces lower context, offloading changes, or frequent memory contention.[unverified]

DSpark’s target-specific design also means the experiment must match the exact target family and likely the intended target/draft pairing.[unverified] It would be unsafe to infer that a Qwen3-8B draft is useful for AJ’s currently served model without checking compatibility and memory use.[unverified]

### Proposed benchmark matrix

Run each condition with the same prompt fixture, context limit, output limit, server build, sampler settings, and thermal state.[unverified]

| Condition | Purpose |
|---|---|
| Baseline, no speculation | Establish current latency, decode rate, and output reference |
| `ngram-mod` | Measure low-memory self-speculation and repetition sensitivity |
| DSpark, if a target-matched draft fits | Measure neural-draft speedup and memory cost |
| Baseline repeated after speculative runs | Detect thermal/cache/order effects |

Use at least four prompt classes: short conversational replies, long-form explanation, code/tool-style structured output, and reasoning-heavy prompts.[unverified] Include the actual system/chat template used by the Spark service.[unverified]

Record:

- time to first token;
- total request latency;
- generated tokens per second;
- prompt processing time;
- output token count;
- draft acceptance rate and accepted tokens, when available;
- queue wait, if the service exposes it;
- peak VRAM/RAM and model-load time;
- HTTP errors, truncated output, malformed structured output, and empty replies;
- exact server/model/build arguments.

Report medians and tail percentiles, not just a single average.[unverified] A speculative mode that improves average decode speed but worsens first-token latency or produces occasional empty/tool-invalid replies is not an automatic win.[unverified]

### Suggested decision gates

1. **Compatibility gate:** the target and draft load successfully with the intended context and GPU-offload settings.
2. **Correctness gate:** deterministic baseline and speculative runs produce identical output on a fixed greedy fixture.
3. **Reliability gate:** no increase in empty replies, failed requests, malformed JSON/tool calls, or cancellation failures.
4. **Latency gate:** p50 and p95 end-to-end latency improve for the workloads AJ actually cares about.
5. **Resource gate:** the speedup does not require an unacceptable reduction in context size or create memory instability.
6. **Operational gate:** acceptance statistics and errors are visible enough to diagnose regressions.

Keep the mode only if it passes all six gates.[unverified] Otherwise retain the baseline and treat the measurements as evidence about workload shape rather than as a failed research direction.[unverified]

## Recommended next experiment

Build a disposable benchmark wrapper around the existing Spark HTTP endpoint or llama-server invocation; do not change the production service defaults.[unverified]

1. Capture the exact current model name, llama.cpp commit/build flags, server arguments, context size, and sampler settings.
2. Create a fixed JSONL prompt fixture with the four workload classes above.
3. Run three repeated baseline trials and save raw responses plus timing/log output.
4. Run `ngram-mod` in an isolated server process using conservative settings, then repeat the fixture.
5. If the build and memory budget permit, obtain the target-matched DSpark draft and repeat with deterministic greedy decoding.
6. Compare output bytes, latency distributions, decode rates, acceptance, and memory use programmatically.
7. Only after the deterministic test passes, run a small sample with AJ’s real production sampling and tool/structured-output paths.

**Decision rule:** do not deploy speculative decoding globally on the basis of upstream speedup alone. Adopt it only if the local fixture shows a repeatable end-to-end benefit without correctness, resource, or reliability regressions.[unverified]

## Uncertainty and open questions

- No local Spark benchmark was run in this report; all performance figures are upstream reports.[2]
- The retrieved sources do not establish the memory footprint of the exact DSpark target/draft pair AJ would use.[unverified]
- The effect of speculative decoding on thinking-enabled versus thinking-disabled Qwen3 behavior was not established.[unverified]
- The effect on streamed cancellation, tool calls, JSON schemas, and long-context requests needs direct testing.[unverified]
