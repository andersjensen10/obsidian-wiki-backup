## Result

The selected topic is **llama.cpp structured outputs and safe parsing for Agora**.

## Bottom line

Use constrained decoding as a **validation aid, not as a replacement for application-level parsing and fallback behavior**. For Agora, the safest boundary is:

1. Keep the user-visible prose turn independent from optional structured extraction.
2. Request a small, explicit JSON schema for the structured side-call or enrichment payload.
3. Validate and parse the returned JSON locally.
4. If parsing or validation fails, preserve the raw prose and record a structured-extraction failure rather than blanking or rejecting the whole turn.
5. Maintain a disposable compatibility test against the exact Spark `llama-server` build before relying on a provider’s claimed `response_format` support.

This follows the shape of llama.cpp’s own interfaces: the server exposes JSON-schema-constrained generation, but the schema is not shown to the model, and unsupported schema features may be skipped silently.[1][2] The official structured-output test script also treats structured output, tool loops, streaming, and `reasoning_content` as separate cases rather than assuming one happy path.[5]

## What the primary sources establish

### 1. llama.cpp has several structured-output entry points

The server supports grammar-constrained generation and JSON Schema inputs, including a `json_schema` request field and OpenAI-compatible `response_format` forms for chat completions.[1][2] The command-line server also exposes parallel slots, which matters when a structured side-call competes with ordinary chat traffic.[1]

GBNF grammars can force outputs into a formal language, including valid JSON, and JSON Schema can be converted into a grammar for supported schema features.[2] This is a decoding constraint: it narrows what tokens may be emitted; it is not equivalent to a semantic validator for every business rule.

### 2. The schema is not prompt content

llama.cpp’s grammar documentation explicitly warns that the JSON Schema is used to constrain output but is not injected into the prompt.[2] The model therefore needs the expected structure described in the prompt as well as the decoding constraint. For Agora, the prompt should name the fields, permitted values, and what each field means; the schema should enforce the machine-readable shape.

### 3. Schema support is deliberately partial

The PEG/parsing documentation also shows that grammar generation and parsing are separate layers, with schema-aware grammar construction handled as a distinct step.[3] That reinforces the application boundary: decoding can shape the output, but Agora still needs an explicit parse-and-validate step before persisting typed state.

The JSON-Schema-to-grammar path documents supported and unsupported features, including a warning that unsupported features may be skipped silently.[2] The current grammar behavior also defaults `additionalProperties` to `false`, which can be useful for compact sidecar payloads but can reject fields that a later schema revision adds unless the contract is versioned carefully.[2]

The optional LLGuidance backend has different defaults: its documentation says `additionalProperties` defaults to `true`, although callers can explicitly set it to `false`.[4] This means switching decoding backends can change acceptance behavior even when the nominal JSON Schema is unchanged. A backend switch should therefore be treated as a compatibility change, not a transparent performance tweak.

### 4. Reasoning output is a separate concern

The server exposes explicit reasoning controls and can return reasoning separately from ordinary content.[1] The structured-output test fixture collects `reasoning_content` independently and supports applying `response_format` either during a whole tool loop or only on the final structured call.[5] That is a useful model for Agora: keep chain-of-thought/reasoning transport separate from the user-facing answer and apply strict structure at the narrowest call that actually needs it.

### 5. An accepted request is not enough evidence

A current llama.cpp issue reports a build that accepted an OpenAI-compatible `json_schema` request with HTTP 200 while failing to enforce the schema, producing ordinary unconstrained text instead.[6] This is an issue report rather than a guarantee that every build behaves this way, but it establishes the operational risk: checking only the HTTP status or seeing one output that happens to match the schema is insufficient.

## Recommended Agora design

### Separate primary content from optional structured enrichment

For narrator/persona turns, persist and display the normal prose stream first. Run structured extraction as an enrichment path that can attach a decision, relationship update, fact, or other typed payload. A malformed or absent payload should not erase the prose turn.

A useful internal result shape is conceptually:

```text
{
  content: string,
  structured: ParsedPayload | null,
  structured_status: "ok" | "invalid_json" | "schema_mismatch" | "unsupported" | "transport_error",
  structured_raw: string | null
}
```

The raw structured text should be retained only under an appropriate debugging/privacy policy; it should not automatically become user-visible content.

### Use a narrow schema

Prefer a small, versioned object with explicit enums and nullable fields over a large schema that attempts to encode the entire conversation state. Narrow schemas reduce decoding work, make failures diagnosable, and limit accidental coupling to model phrasing.

For example, an optional scene-decision payload might contain `schema_version`, `decision`, `confidence`, and `rationale_summary`, with `decision` restricted to a short enum. Keep long prose outside the structured object unless the application genuinely needs to parse it.

### Prompt the structure explicitly

Because the schema is not visible to the model,[2] the prompt should include a compact human-readable contract. State whether the response must be only JSON, give one valid example, define enum semantics, and say what to emit when no decision applies. Do not depend on the schema alone to teach the model the task.

### Test adversarially against the served build

The test should include at least:

- a minimal object that must satisfy a required enum;
- an object with an intentionally forbidden extra property;
- a nested array/object case;
- a malformed or unsupported schema feature;
- streaming and non-streaming requests;
- a reasoning-enabled request;
- a tool loop followed by a final structured call;
- a model response that deliberately attempts prose before JSON.

The acceptance condition is not merely HTTP 200. Parse the response, validate it independently, assert that forbidden fields are absent, and record whether the server rejected, constrained, or silently ignored the requested format. The upstream structured-output fixture is a useful starting point because it already exercises response-format variants, streaming, tool use, and reasoning-content capture.[5]

## Practical experiment

Build a disposable `scripts/live-structured-output-check.mjs` or equivalent fixture against the current Spark endpoint. It should:

1. Read the served model alias rather than hardcoding it.
2. Send one ordinary chat request as a control.
3. Send the same prompt with a deliberately strict schema.
4. Validate the returned JSON locally with a real schema validator.
5. Send an adversarial prompt asking for an extra property and confirm the application’s validator rejects it if the server lets it through.
6. Repeat with streaming enabled.
7. Repeat with reasoning enabled and verify that reasoning remains separate from `content`.
8. Emit a machine-readable result showing request shape, HTTP status, parse status, validation status, and observed extra keys.

Run the fixture against the exact Spark build before enabling any production Agora path that assumes schema enforcement. If the server fails the constraint test, keep the structured call behind local validation and repair/retry logic; do not treat `response_format` as authoritative.

## Trade-offs and uncertainty

- **Constrained decoding improves shape reliability but does not guarantee semantic correctness.** A valid enum can still be the wrong decision for the scene. Business rules and authorization remain application responsibilities.
- **A schema can reduce model freedom.** Overly strict schemas may cause truncation, empty output, or brittle behavior, especially when reasoning consumes the available token budget. The structured call should have an explicit token budget sized for both reasoning and the final object.
- **Backend differences matter.** The documented defaults differ between the current grammar path and LLGuidance, so a backend change can alter acceptance behavior.[2][4]
- **The issue report is a warning signal, not a universal diagnosis.** It documents one reported failure mode in a particular build; the exact prevalence for AJ’s current Spark build is unknown.[6]
- **No performance claim is made here.** The sources establish interfaces and behavior, not the latency or throughput impact on AJ’s specific model and hardware. That requires measurement on Spark.

## Why this matters to AJ

Agora already has the difficult architectural requirement: structured model output must enrich a turn without gating the turn. This research gives a concrete implementation boundary for that rule. The highest-value next step is not another framework integration; it is a small compatibility-and-adversarial fixture against the live Spark model, followed by a narrow schema for one real Agora side-call.
